## 1. Back-end em Node.js
Uma linguagem só (TypeScript) no front e no back, com tipos compartilhados entre eles.

## 2. Express como framework da API
Escolhido por ser familiar. Complementos: `multer` (uploads), Zod (validação), `helmet`, `cors`, `express-rate-limit`, `pino-http`.

## 3. Multitenant desde o início
- Banco compartilhado com coluna `tenant_id` em todas as tabelas de dados. Isolamento na aplicação e reforçado por Row Level Security no Postgres (ver decisão 9).
- Usuário pode pertencer a vários tenants (tabela `Membership`).
- Arquivos, jobs de fila, integrações e limites de uso sempre separados por tenant.

## 4. Transcrição com AssemblyAI
- Recursos: `speaker_labels`, `language_code: 'pt'`, timestamps, `word_boost` por tenant, redação de PII.
- Fluxo assíncrono via webhook, validado por segredo.
- Uso contabilizado por tenant; a transcrição é apagada no AssemblyAI depois de salva no Fluxi.

## 5. draw.io via `embed.diagrams.net`
- Editor em iframe (`embed=1&proto=json`), com comunicação por `postMessage`.
- Fluxo: `init` → `load(xml)` → `autosave`/`save` → `export(png/svg)` para o POP.
- O XML fica no banco do Fluxi (PostgreSQL) (com `tenant_id` e versão); o draw.io não armazena nada.
- Licença Apache 2.0.
- **Futuro:** migrar para draw.io auto-hospedado (`jgraph/docker-drawio`) quando clientes exigirem que os diagramas não saiam da infraestrutura do Fluxi.

## 7. Claude Sonnet 5.5 via API da Anthropic
- Modelo `claude-sonnet-5-5` pelo SDK oficial `@anthropic-ai/sdk` (US$ 2 / US$ 10 por MTok de entrada/saída, mesmo preço do Sonnet 5, que era a escolha anterior).
- Comparação (set/2026): Haiku 4.5 US$ 1/5 (mais barato, erra mais em reuniões longas); Opus 5.5 US$ 4/20 (desnecessário). Custo estimado por fluxograma de uma reunião de 1 h: ~US$ 0,09.
- Fallback no servidor (`fallbacks: "default"`) para recusas indevidas do filtro de segurança.
- Chave com workspace: `ANTHROPIC_API_KEY` + `ANTHROPIC_WORKSPACE_ID`.
- Descartado o LLM Gateway do AssemblyAI: não oferece o Sonnet 5, e o Sonnet 4.6 de lá custa US$ 3 / US$ 15.
- Saída estruturada (`output_config.format`) com o `PopSchema`, validada com Zod.
- Batch API (-50%) para extrações sem urgência; cache de prompt para instruções e schema fixos.
- Extração isolada em `packages/ai` (`extrairPop(transcricao)`) para permitir troca de modelo/fornecedor.
- Estimativa: ~US$ 0,08 de LLM + ~US$ 0,23 de transcrição por hora de reunião.
- LGPD: Anthropic passa a ser processadora de dados (incluir nos termos).

## 9. Banco de dados PostgreSQL 17 (Absam)
- **Troca:** o MySQL da HostGator (5.7.44, fora de suporte desde 2023, sem RLS/CTEs/`CHECK`) foi descartado. O banco do Fluxi será **PostgreSQL 17 hospedado na Absam** (absam.io), com dados no Brasil (bom para a LGPD).
- Credenciais **somente** por variáveis de ambiente (`DATABASE_URL` ou `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`), nunca com valor padrão no código nem versionadas. `.env` fica no `.gitignore`. Conexão sempre com SSL.
- Usuários separados: um dono do schema (migrações) e um da aplicação, **sem** `BYPASSRLS` e sem ser dono das tabelas, com permissões mínimas.
- **Multitenant com duas travas:**
  - toda tabela de dados tem `tenant_id` + índice composto começando por `tenant_id`;
  - camada de repositório que exige o `tenantId` em toda consulta;
  - **Row Level Security** em todas as tabelas de tenant: a aplicação abre a transação com `SET LOCAL app.tenant_id = '...'` e as políticas filtram por `tenant_id = current_setting('app.tenant_id')::uuid`;
  - testes automáticos que tentam ler/alterar dados de outro tenant e precisam falhar.
- Recursos usados: `uuid` (`gen_random_uuid()`), `JSONB` para FluxoSchema/PopSchema, `CHECK` para regras simples, `timestamptz`, busca textual com dicionário `portuguese`. Futuro: `pgvector` para busca semântica, se a Absam permitir a extensão.
- ORM: a definir (Prisma ou Drizzle; Drizzle facilita o `SET LOCAL` por transação para o RLS).
- Pontos a verificar na Absam: se é banco gerenciado ou VPS, backups automáticos (e retenção), limite de conexões (usar pool/PgBouncer se for baixo), acesso remoto com SSL, extensões disponíveis.
- Arquivos (áudio, vídeo, imagens) não ficam no banco: vão para um storage de objetos, com o caminho salvo no Postgres.

## 11. Supabase no MVP e nos testes
- Banco (Postgres, com RLS) e arquivos (Supabase Storage) do MVP ficam no Supabase. A produção segue prevista no Postgres 17 da Absam (decisão 9); o schema é Postgres puro, então a migração é direta.
- Evitar prender o código ao Supabase: migrações em SQL versionadas no repo, acesso ao banco pelo ORM via connection string e storage atrás de uma interface (`packages/core/storage`), para trocar por S3/Absam depois.
- Storage: buckets privados, caminho `tenants/{tenant_id}/...`, acesso só por URLs assinadas geradas pela API.
- A chave `service_role` fica só no back-end (API/worker), nunca no front-end.
- Configuração pelo conector Supabase (MCP) ou pela Management API (HTTPS); a porta 5432 não é acessível do ambiente de desenvolvimento em nuvem.

## 12. Next.js no front, Node.js + Express no back
- **Motivo:** o Fluxi será um produto com páginas públicas (landing, preços, cadastro de empresas, links públicos de POP/fluxograma), que precisam de SEO e carregamento rápido. O Next.js atende o site público e o app no mesmo projeto. Vite foi considerado e descartado por esse motivo.
- **Front-end:** Next.js (App Router) com React e TypeScript, usado **só como front**:
  - páginas públicas renderizadas no servidor (SEO);
  - área logada (`/app/...`) com componentes de cliente; o editor draw.io e o gravador de tela/áudio carregam só no navegador (`"use client"` + import dinâmico);
  - login com Supabase Auth via `@supabase/ssr` (sessão em cookie httpOnly, rotas protegidas no middleware).
- **Sem API Routes/Server Actions para regra de negócio:** toda regra fica na API Express, para não haver duas APIs. O Next pode usar rotas próprias só para coisas de front (ex.: callback do login).
- **Back-end:** Node.js + Express (decisão 2); tipos e schemas compartilhados em `packages/core`.
- **Variáveis do front** usam o prefixo `NEXT_PUBLIC_` (só URL e chave `anon` do Supabase). As secretas ficam só no back.
- **Hospedagem no MVP:**
  - Vercel: Next.js e API Express (como funções);
  - uploads de áudio e vídeo vão direto do navegador para o Supabase Storage, com URL assinada gerada pela API (a Vercel limita requisições a ~4,5 MB);
  - worker (fila, ffmpeg, IA, geração de POP e fluxograma) roda fora da Vercel, num processo contínuo (Railway, Render ou Fly.io). Fila a definir: BullMQ + Redis ou `pgmq` no Supabase.

## 13. MVP: API nas rotas do Next.js, sem login, IA por créditos
- **API:** no MVP, as rotas ficam em `app/api/*` (Next.js, funções na Vercel), para um único deploy. A regra de negócio fica em `lib/server/*`, sem depender do Next, para ser movida para o Express (decisão 2) quando o worker e a API separada entrarem.
- **Sem login por enquanto:** tudo usa um tenant padrão (INC). O acesso ao Supabase é só pelo servidor, com a chave `service_role`; RLS ligado e sem políticas, então a chave pública não lê nada. Login e RLS por membro entram depois.
- **Fluxogramas no Supabase:** tabela `fluxogramas` (XML, FluxoSchema, origem `manual`/`ia`/`modelo`, miniatura). Migração em `supabase/migrations/0001_fluxogramas.sql`.
- **IA por créditos** (suspenso pela decisão 20)**:** cada empresa tem `creditos_ia`. Gerar fluxograma custa 1 crédito; transcrever áudio, 1. Débito atômico no banco (`debitar_creditos`) e registro em `uso_ia`. Sem créditos, a IA fica bloqueada e o usuário continua **criando manualmente**.
- **Três jeitos de gerar com IA:** descrição do processo, transcrição colada/arquivo (.txt, .vtt, .srt) e áudio/vídeo (vai para o Storage, é transcrito pelo AssemblyAI e segue para a IA).
- **Geração:** Claude Sonnet 5 devolve o FluxoSchema (saída estruturada) e o código monta o XML com os estilos da biblioteca BPMN INC (`lib/fluxo/`), já editável no draw.io.

## 14. Gravação → POP + fluxograma (AssemblyAI barato)
- **Modelo de transcrição:** `universal-3-5-pro` com fallback `universal-2` (padrão do AssemblyAI para arquivo gravado). US$ 0,21/h, português com sotaque brasileiro. Diarização (`speaker_labels`) +US$ 0,02/h. Nenhum outro add-on pago (PII, entidades, keyterms, resumo).
- **Universal-3.6 Pro não serve aqui:** é só para streaming (tempo real), a US$ 0,45/h. Como a gravação já existe, o arquivo gravado sai por menos da metade do preço.
- **LGPD:** depois de salvar o texto no Fluxi, a transcrição é apagada no AssemblyAI (`DELETE /v2/transcript/{id}`). No plano pago, configurar TTL e opt-out de treino em Data Controls.
- **Fluxo:** um job de transcrição por segmento de 3 min (tempos somados ao início do segmento). O navegador consulta a cada 5 s e cada consulta avança o processamento (sem fila). Quando tudo está transcrito, uma trava atômica no banco garante que só uma requisição chama o Claude, que devolve **POP + fluxograma + instrução de cada tela numa chamada só**, para enviar a transcrição uma vez.
- **Custo:** 3 créditos (transcrição, fluxograma, POP). Numa nova tentativa, as partes já transcritas são reaproveitadas. Custo real aproximado por 1 h de gravação: ~US$ 0,23 de transcrição + ~US$ 0,10 a 0,20 de Claude.

## 15. Processo como pasta
- **Processo** (`processos`) é a unidade de navegação: cada um tem código, nome e área, e reúne as gravações (com a transcrição), os fluxogramas e os POPs dele. A tela inicial é a lista de processos.
- Os itens têm `processo_id`. Quem é criado dentro do processo já nasce nele; o POP herda o processo do fluxograma ou da gravação de origem, e a geração com IA a partir de uma gravação coloca POP e fluxograma no mesmo processo.
- Excluir o processo exclui só a pasta: os itens continuam nas listas de "Todos os itens", sem processo. Assim nada se perde por engano.
- Os itens que já existiam foram migrados: um processo por fluxograma, com o mesmo código e nome, junto dos POPs e gravações ligados a ele (`0005_processos.sql`).

## 16. Organização → Área → Processo → itens
- A navegação (e, com o login, o acesso) segue: **Organização → Área → Processos da área → gravações, fluxogramas e POPs do processo**. A tela inicial passou a ser o Início, centrado no POP (decisão 21).
- **Conta (tenant) ≠ organização:** a conta é quem usa o Fluxi (créditos de IA e, depois, usuários); a organização é a empresa cujos processos são modelados. Uma conta modela várias organizações (`0007_organizacoes.sql`). Nome de área é único dentro da organização; organização só é excluída sem áreas. As áreas que existiam foram para "INC Empreendimentos".
- Todo processo pertence a uma área (`processos.area_id`, obrigatório). O processo pode ser movido de área; a área só pode ser excluída vazia. Nome de área é único por empresa.
- O POP criado num processo já vem com a área preenchida.
- **Acesso (quando entrar o login):** cada pessoa recebe as organizações e/ou áreas que pode ver ou editar (membros por organização e por área), e as consultas e o RLS filtram por elas. Hoje, sem login, todos veem tudo.
- Os processos que já existiam foram para a área "Geral" (`0006_areas.sql`). A coluna texto `processos.area` ficou só por compatibilidade.

## 17. Contas, pessoas e convites
- **Conta (tenant)** é de quem usa o Fluxi; a pessoa que cria a conta é a **dona**. Os créditos de IA são da conta.
- A conta **convida pessoas por e-mail**. Quem convida escolhe o papel (admin vê tudo; membro vê só o liberado) e **quais organizações** o convidado enxerga e pode editar (`membros`, `membro_organizacoes`, `convites`, em `0008_membros_convites.sql`).
- **Uma pessoa pode estar em várias contas:** a própria (com suas organizações) e as em que foi convidada. Ao entrar, escolhe a conta em que vai trabalhar, e tudo (organizações, áreas, processos, créditos) é dessa conta.
- Isso depende do **login**. Recomendação: Supabase Auth (e-mail com link mágico e Google), pois já é o MVP no Supabase e o RLS passa a filtrar por membro. Enquanto não há login, tudo usa a conta padrão INC.

## 18. Marcações na tela (caixa, seta, número, texto, recorte)
- Em cada tela marcada dá para desenhar **caixa, seta, número (ordem dos cliques) e texto**, e **recortar**. Cor padrão vermelha (#E5252A), com amarelo, verde, azul e preto como alternativas. Desfoque ficou de fora por decisão do produto.
- **Onde:** na página da gravação (botão "Marcar" ou clique na imagem) e no passo do POP ("Marcar tela"). A marcação é **da tela da gravação**: editar num lugar muda nos dois e em todo POP que usa a tela.
- **Sem estragar o original:** o print fica intacto; as formas ficam em `gravacao_marcacoes.anotacoes` (pixels da imagem original), para reabrir e editar. Ao salvar, o navegador gera a imagem final (desenhada e recortada, na resolução original) e envia ao Storage; o POP e o DOCX usam essa versão (`imagem_anotada_caminho`, com largura e altura próprias por causa do recorte). A versão anterior é apagada a cada salvamento (`0009_marcacao_anotacoes.sql`).
- **Biblioteca:** react-konva (MIT), carregada só quando o editor abre. Descartado o marker.js (linkware/licença paga).
- **Não é possível** capturar onde a pessoa clicou durante a gravação: o navegador não informa cliques em outros programas. A **sugestão automática da caixa pela IA** (Claude localiza o elemento citado na instrução, ~US$ 0,005 por tela, sempre editável) fica para depois.

## 19. Modelo POP v3 (27/10/2026), PDF e fim dos exemplos
- **Modelo novo:** título "POP - Procedimento Operacional Padrão", ícones nas seções, faixa decorativa, "Históricos de Revisões" e procedimentos só como **print + caixa "Passo N:"** (sem a tabela de nome × tópicos). O template é regenerado do `.docx` original pelo script; trocar o modelo = trocar o arquivo e rodar `npm run modelo-pop`.
- **Campo novo "Elaborado por"** (`pops.autor`): quem criou o POP. Hoje a pessoa preenche; com o login, vem do usuário. Preenche as linhas do histórico sem nome.
- **PDF gerado pelo sistema** com pdfmake (MIT, JavaScript puro), e não por conversão do DOCX: na Vercel não há LibreOffice, e um serviço externo de conversão custaria por arquivo e dependeria de terceiro. O PDF reproduz o modelo (fonte Roboto no lugar da Aptos, que é proprietária). Os dois formatos saem do mesmo conteúdo (`DadosPop`), então mudanças de layout são feitas nos dois geradores.
- **Exemplos removidos:** o fluxograma de amostra ("Exemplo EmCash") e seus arquivos, e os textos de exemplo com nomes de empresa e área nas telas. O que fica são dicas genéricas ("Nome da área").

## 20. Créditos de IA suspensos
- **Por enquanto não há contagem nem limite de créditos.** A IA (gerar fluxograma, transcrever, gerar POP e fluxograma a partir da gravação) funciona sem verificar saldo e sem debitar. Saiu da tela o contador de créditos e os textos de custo.
- O controle de gasto fica nos painéis da Anthropic e do AssemblyAI (limites de uso por conta/workspace).
- **No banco nada foi apagado:** `tenants.creditos_ia`, a tabela `uso_ia` e a função `debitar_creditos` continuam lá, sem uso pelo app, para voltar com a cobrança por créditos quando entrar o plano comercial (substitui a parte de créditos da decisão 13).

## 21. Navegação centrada no POP
- **O produto final é o POP e a gestão dos POPs.** Gravações e fluxogramas são materiais de apoio para chegar ao POP, e a navegação passou a refletir isso; antes, era organizada pela estrutura (organizações, gravações, fluxogramas).
- **Início** (`/app/inicio`, a tela de entrada): números de POPs publicados, em rascunho e processos sem POP; "Continue de onde parou" (rascunhos recentes); processos sem POP, com atalho para documentar; botão "Documentar um processo".
- **Menu:** Início e POPs no topo; "Estrutura" (Organizações, que inclui áreas e processos); "Materiais de apoio" (Gravações, Fluxogramas); "Conta". No celular o menu vira uma barra no topo (antes sumia e não havia navegação).
- **POPs (gestão dos documentos):** busca por nome, identificação, código, área ou processo; filtro por status com contagem; cada linha mostra onde o POP está (organização · área · processo), versão, data, status e download em PDF e DOCX. Todo POP novo nasce num processo: o "Novo POP" pede o processo.
- **Status do POP:** rascunho ou publicado (`pops.status`), com o botão "Publicar" / "Voltar para rascunho" no editor. Ainda não gera versão nova ao publicar.
- **Página do processo começa pelo POP:** sem POP, mostra três caminhos (gravar a tela, recomendado; escrever o POP; começar pelo fluxograma); com POP, o POP em destaque com status e downloads. Gravações e fluxogramas ficam abaixo, como materiais de apoio.
- **Editor do POP:** trilha Organização › Área › Processo (POP sem processo pode ser vinculado ali) e o fluxograma só lista os do mesmo processo.
- **Gravação:** "Nova gravação" a partir do processo já vem com o processo escolhido. Com áudio pronto, a ação principal é gerar o POP com IA; "Criar POP sem IA" fica como secundária.

## 22. Layout do fluxograma gerado pela IA
- **Problema:** o fluxograma gerado pela IA saía embaralhado. Cada nó ia para a coluna da menor distância desde o início, então havia setas voltando para trás e cruzando caixas, textos cortados dentro dos círculos de início e fim e anotações por cima das raias. A biblioteca de estilos já era a da INC (`templates/drawio/biblioteca-estilos.xml`, a mesma do arquivo "instruções drawio"); o problema era o posicionamento.
- **Decisão:** layout em camadas próprio, pensado para raias horizontais (detalhes em `docs/fluxograma.md`): laços separados, coluna pela maior distância, trilhas dentro da raia e setas roteadas pelos corredores. Bibliotecas genéricas de layout (ELK, dagre) não tratam raias e ficariam pesadas no navegador; a do próprio draw.io também ignora raias.
- **Mais fiel à biblioteca:** etiqueta roxa da área, seta com losango na saída, Indicador de Caminho Sim/Não, pergunta do gateway como Caixa de Texto de Condição, "Início"/"Fim" no círculo com o texto embaixo, nota e alerta com os estilos da biblioteca.
- **IA:** o prompt passou a trazer o glossário da biblioteca (quando usar cada tipo de início, fim, link e gateway).
- **Fluxogramas já gerados:** "Refazer no padrão INC" no editor recria o diagrama a partir da estrutura original da IA, com confirmação (perde as edições manuais).

## 23. Pausar e retomar (gravação e POP) e prints anexados no POP
- **Gravação pausável entre sessões.** "Pausar" fecha a parte do vídeo em andamento e a envia na hora (antes, a pausa só segurava o MediaRecorder e a parte ficava na memória até encerrar). Com isso, o que foi gravado até a pausa está salvo mesmo que a aba feche. Na pausa aparece "continuar outro dia": libera a tela e deixa a gravação com status `pausada`.
- **Continuar de onde parou:** `/app/gravacoes/nova?continuar=<id>` reabre a tela e o gravador recebe o tempo já gravado e o índice da próxima parte; o relógio, as partes (`inicio_ms`) e as telas marcadas (`tempo_ms`) seguem em sequência, e o player toca tudo junto. Vale para gravação pausada, não finalizada (aba fechada no meio: status `gravando` sem aba aberta) e até pronta ("Continuar gravando", para acrescentar). A transcrição reaproveita as partes já transcritas. "Finalizar assim" marca como pronta sem compartilhar a tela de novo.
- **Telas novas no POP existente:** quando a gravação já tem POP (gerado pela IA ou criado "com estas telas") e ganha telas depois, a página da gravação oferece "Levar as telas para o POP": entram como passos de um procedimento novo no fim, sem gerar outro POP. Cada tela mostra o selo "No POP".
- **POP retomável no ponto exato.** O editor guarda onde a pessoa está (`pops.posicao`: `{ chave, rotulo }`, ex.: "Passo 3 do procedimento 2"), salvo 2 s depois de mudar de campo e ao sair da página, separado do autosave do conteúdo. "Pausar e sair" salva tudo, guarda a posição e volta ao processo. Os links "Continuar" (processo e Início) abrem com `?retomar=1`: a página rola até o campo, foca e destaca. Sem `?retomar`, um chip "Você parou em…" leva até lá. O Início lista também as gravações pausadas ou não finalizadas.
- **Prints anexados direto no POP.** Em qualquer passo: "Anexar print" / "Trocar print" / "Adicionar passo com print", com três caminhos: capturar uma janela agora (`getDisplayMedia` de um quadro só, encerrado em seguida), colar (botão com `clipboard.read()` ou Ctrl+V com o passo focado) ou escolher arquivo (PNG/JPG/WebP, convertido para PNG). O print pode ser marcado (caixa, seta, número, texto, recorte) como as telas da gravação.
- **Modelo de dados:** a tela do POP fica na mesma tabela das telas marcadas (`gravacao_marcacoes`), agora com dono `gravacao_id` **ou** `pop_id` (`tempo_ms` só nas da gravação) e arquivo em `tenants/<tenant>/pops/<pop>/`. As rotas de anotação e exclusão existem nas duas famílias (`/api/gravacoes/:id/marcacoes/:mid` e `/api/pops/:id/telas/:tid`) sobre o mesmo código (`lib/server/telas.ts`). Remover a imagem de um passo apaga o print do POP (o da gravação fica na gravação); excluir o POP apaga a pasta.

## 24. PDF fiel ao DOCX do modelo
- **Problema:** o PDF não seguia o DOCX. A faixa do topo saía laranja (no Word ela é cinza: o modelo aplica um efeito duotone com a cor do tema e 85% de opacidade); o espaçamento era cerca de 20% mais apertado (os parágrafos vazios que o modelo usa como espaçadores, a entrelinha de 1,5 do cabeçalho, as alturas mínimas e as margens das células não eram reproduzidos); o "negrito" era a Roboto Medium; a numeração dos envolvidos, as bordas e as faixas do histórico diferiam. (O DOCX que parecia "certo" na comparação era de antes do Modelo v3.)
- **Por que continua pdfmake e não conversão do DOCX:** converter com o Word ou o LibreOffice exigiria um servidor com esses programas (a Vercel não tem) ou um serviço pago de terceiro. Em vez disso, o gerador passou a seguir o modelo parágrafo por parágrafo, com as regras do Word medidas no PDF que o próprio Word exporta: linha de 1,222 × fonte × entrelinha, texto no topo da linha, espaçadores, margens de célula (108 twips), alturas mínimas e alinhamento vertical, deslocamentos das âncoras (ícones, réguas, faixa), moldura de 4 pt da logo, listas "1."/"A." com os recuos do modelo, Plain Table 1/2 e Table Grid Light. Conferido contra o DOCX renderizado: posições a poucos pontos e as mesmas quebras de página.
- **Efeitos de imagem do Word** (duotone, opacidade) são "assados" no PNG por `npm run modelo-pop`, lendo os parâmetros do próprio DOCX; se o modelo mudar, o PDF acompanha ao rodar o script.
- **Fonte:** Roboto (OFL), a fonte livre de largura mais próxima da Aptos (3% mais larga; a Inter, que o LibreOffice usa, é 9%). Negrito agora com a Roboto Bold.
- **Se um dia precisar ser idêntico ao Word:** converter o DOCX pelo Microsoft Graph (o Word da própria conta Microsoft 365 da INC gera o PDF) ou por um serviço de conversão; exige configuração no Azure ou custo por arquivo.

## 25. Mover o POP para outra área
- **Decisão:** a área do POP é a do processo dele, então mover o POP leva o **processo inteiro**, com tudo o que tem (os outros POPs, as gravações e os fluxogramas). A janela mostra o que vai junto antes de confirmar. Não há "só este POP": separar um POP do processo deixaria a gravação e o fluxograma dele para trás.
- **Onde:** botão "Mover" no editor do POP e na lista de POPs (`POST /api/pops/:id/mover`). A área pode ser de qualquer organização; o seletor de área da página do processo, que faz a mesma coisa, passou a listar também as áreas das outras organizações.
- **Substituída pela decisão 36** (04/11/2026): o "Mover" do POP passou a levar o POP para **outro processo**; mover para outra área é feito pelo processo (seletor de área ou "Mover ou copiar" na página dele).
- **POP sem processo:** entra num processo da área escolhida, existente ou criado na hora.
- **Campo "Área" do documento:** acompanha a área nova quando estava em branco ou com o nome da área antiga; se a pessoa escreveu outra coisa, fica como está. Vale para todos os POPs do processo, também quando a área muda pela página do processo.

## 26. Confirmações e avisos no próprio site
- **Decisão:** nada de `confirm()`/`alert()` do navegador (mostram "fluxi-khaki.vercel.app diz", fogem do visual e travam a página). `confirmar({ titulo, mensagem, acao, perigo })` e `avisar(titulo, mensagem)` (`components/Dialogos.tsx`) abrem um diálogo do site e devolvem uma Promise; `<Dialogos />` fica no layout raiz e mostra um pedido de cada vez.
- **Comportamento de diálogo nativo:** o foco vai para o botão de ação e volta para quem pediu ao fechar; Esc cancela; Tab circula entre os botões; os atalhos da tela por baixo não recebem teclas (ex.: Delete no editor de marcação). Ações destrutivas têm o botão vermelho. Em tela cheia (editor de fluxograma), o diálogo é desenhado dentro do elemento em tela cheia.
- **Única exceção:** o aviso de "sair da página com alterações não salvas" continua sendo o do navegador; por segurança, nenhum site pode trocar esse.

## 27. Partes da gravação ilegíveis ("Transcoding failed")
- **Defeito:** na troca de parte (a cada 3 min), o gravador fechava o recorder antigo e abria o novo na hora, mas o último pedaço do antigo (até 1 s) só chega depois do `stop()`. Como os dois usavam a mesma lista de pedaços, esse pedaço entrava no começo da parte nova, antes do cabeçalho. Toda parte depois da primeira começava no meio do vídeo: nenhum programa abria (o AssemblyAI respondia "Transcoding failed... application/octet-stream (data)"), e a parte anterior perdia o último segundo. As partes depois de uma pausa não tinham o defeito (entre fechar e abrir há tempo para o pedaço chegar).
- **Correção do gravador:** cada recorder guarda os pedaços na própria lista. Conferido com o gravador de verdade no Chromium: todas as partes começam com o cabeçalho WebM e o ffmpeg lê todas.
- **Gravações já feitas:** antes de mandar para a transcrição ("Gerar POP" ou "Tentar de novo"), o Fluxi confere o começo de cada parte (1 MB). Se há uma sobra antes do cabeçalho, ela volta para o fim da parte anterior (de onde veio), e a parte ganha a duração no cabeçalho (`lib/gravacao/reparo.ts`). Os arquivos são substituídos no Storage, então o player também volta a tocar essas partes. Se o conserto parar no meio, rodar de novo não duplica nada.
- **Mensagem de erro:** diz qual parte falhou e a partir de que minuto, em português.

## 28. Borrar dados sensíveis nos prints
- **Decisão:** ferramenta **Borrar** (tecla B) no editor de marcação: a pessoa arrasta sobre nomes, CPF, e-mails etc. e a área vira um quadriculado. É manual, feito por quem elabora o POP; a IA não identifica nem borra nada.
- **Como:** o borrão é uma marcação como as outras (`tipo: 'borrar'`, em pixels da imagem original), então dá para mover, redimensionar, desfazer e reabrir depois. O quadriculado reduz a área a um pixel por quadrado (média das cores) e amplia sem suavizar; o quadrado tem 1/96 da largura do print (20 px num print de 1920 px), maior que uma letra. Os borrões ficam logo acima do print, e setas, caixas e números continuam visíveis por cima.
- **Onde vale:** na imagem marcada, que é a usada no editor do POP, no DOCX e no PDF. O print original continua guardado (para reabrir e editar as marcações) e não aparece no POP; o vídeo da gravação também não é alterado.

## 29. Formatação de texto no POP (objetivo e passos)
- **Decisão:** o objetivo e o texto de cada passo ganham uma barra de formatação no editor do POP (aparece por cima do campo enquanto se edita): negrito, itálico, sublinhado, tachado, cor do texto (6 cores), marca-texto (5 cores), lista com marcadores, lista numerada, tabela, limpar formatação, desfazer e refazer. Atalhos: Ctrl+B, Ctrl+I, Ctrl+U, Ctrl+Shift+S, Ctrl+Z; Tab passa para a próxima célula (na última, cria uma linha).
- **Tabela:** inserida pela grade (até 6 × 6), com a primeira linha como cabeçalho; o menu da tabela insere e exclui linhas e colunas, liga/desliga o cabeçalho e exclui a tabela. Colunas de largura igual e sem células mescladas (tabela colada de outro lugar entra sem mesclas): é o que sai igual nos dois formatos. No DOCX e no PDF: borda cinza fina (a mesma dos envolvidos), cabeçalho com fundo cinza e negrito, repetido no topo de cada página, e linhas que não se dividem entre páginas.
- **Fora, de propósito:** fonte, tamanho, títulos, emoji, links, imagens, vídeo e alinhamento. O modelo do POP define fonte e tamanho; prints entram pelo "Anexar print"; o resto não tem como sair igual no DOCX e no PDF.
- **Editor:** Tiptap 3 (ProseMirror), só com as extensões acima. O que se cola de outro lugar passa pelo mesmo filtro: o que não está na lista vira texto simples.
- **Formato salvo:** HTML restrito no mesmo campo de texto (`objetivo`, `passos[].texto`), sem mudar o banco: `<p>`, `<ul>`/`<ol>`/`<li>`, `<table>`/`<tr>`/`<th>`/`<td>`, `<br>`, `<strong>`, `<em>`, `<u>`, `<s>`, `<span style="color">` e `<mark data-color>`. Texto sem HTML (o que a IA escreve e os POPs antigos) continua valendo, uma linha por parágrafo. `lib/pop/texto-rico.ts` lê esse formato sem depender do navegador; tags e atributos fora da lista são descartados (só o texto fica) e cor só vale em `#rrggbb`/`rgb()`.
- **DOCX:** parágrafos e listas de verdade do Word (numeração própria no `numbering.xml`; cada lista numerada recomeça em 1), marca-texto como sombreamento do trecho. O objetivo passou a ser `{@objetivo}` no modelo (`npm run modelo-pop`). **PDF:** os mesmos trechos e listas no pdfmake (Roboto com itálico e negrito-itálico). Conferido lado a lado com o DOCX renderizado.

## 30. Melhorar os textos do POP com IA (Groq)
- **Decisão:** botão de IA (ícone de brilho, roxo) ao lado de cada passo e no título do objetivo. A IA corrige ortografia, gramática e pontuação e deixa o texto mais claro (imperativo, frases curtas, uma ação por frase), **sem inventar** passos, campos, valores ou nomes e mantendo nomes de sistemas, botões e telas como estão. A pessoa vê o texto atual e a sugestão lado a lado, com a lista do que mudou, e escolhe "Usar sugestão", "Manter o meu" ou "Gerar outra"; o "X" no canto e o Esc fecham a qualquer momento, até durante a revisão (a resposta que chegar depois é ignorada). Nada muda sem a escolha; depois de usar, Ctrl+Z no texto volta ao anterior.
- **Modelos:** Groq (API compatível com a da OpenAI, `https://api.groq.com/openai/v1/chat/completions`), `openai/gpt-oss-120b`; se falhar, `openai/gpt-oss-20b`. Conta como falha: limite de uso (429), Groq fora do ar (5xx, 498), demora acima de 25 s, resposta cortada ou fora do formato. Chave recusada (401/403) não tenta o reserva (é a mesma chave). Foi a Groq e não o Claude (que segue para POP e fluxograma) por ser uma tarefa curta, frequente e que pede resposta em 1 a 2 s.
- **Pedido:** uma mensagem só (a Groq recomenda não usar system prompt nos modelos de raciocínio), `reasoning_effort: low`, `include_reasoning: false`, `temperature` 0,3 e resposta em JSON com schema estrito (`texto` e `mudancas`). Vão como contexto o nome do POP, o do procedimento, o número do passo e o texto dos passos vizinhos (só para manter a coerência e a forma verbal).
- **Prompt ajustado aos POPs reais** (9 POPs, 110 passos, lidos em produção): os autores escrevem no imperativo ("Acesse") ou no infinitivo ("Acessar") e os dois aparecem em POPs publicados, então a IA **mantém a forma do autor** e só converte texto narrado ("acessamos", "seguimos") ou na voz passiva; números nos textos ("1 -", "4.") apontam os números marcados no print ou continuam a lista do passo anterior, então a IA **não renumera, não junta nem divide itens**; títulos dentro do passo ficam em linha própria (o primeiro em negrito); ficam como estão nomes de sistemas (RM, TOTVS, Fluig, Agidesk, eSocial…), códigos (S-2220, B31, NR-7), rótulos de tela em MAIÚSCULAS ou entre aspas, links e caminhos de pasta e de menu; textos que são só referência ao print ("2", "caminho pasta") voltam iguais; o objetivo não é encurtado. Três exemplos curtos (antes → depois) vão no prompt. Texto acima de 1.200 caracteres usa raciocínio médio.
- **Conferência dos termos:** mesmo instruída, a IA às vezes deforma um nome (num teste real, "Fluig" virou "FluFlig"). Por isso o servidor confere toda sugestão antes de mostrar (`lib/pop/termos-protegidos.ts`): links, textos entre aspas, códigos com números (S-2220, B31), palavras em MAIÚSCULAS e com maiúscula no meio (eSocial) precisam continuar no texto, e nenhuma palavra nova pode ser uma versão deformada desses termos ou de um nome com inicial maiúscula no meio da frase (Fluig, Agidesk, Salvar): uma letra trocada, letras a mais ou a menos. Acento corrigido, plural e frases juntadas (o nome aparecer menos vezes) não contam. Sugestão reprovada é descartada e o modelo reserva tenta; se os dois errarem, a pessoa vê o motivo (ex.: "“Fluig” virou “FluFlig”") e pode tentar de novo. Testado com 117 textos dos POPs reais e 12 respostas reais da IA, sem alarme falso.
- **Formatação:** o texto vai em HTML do editor (decisão 29) e a IA devolve no mesmo formato. A resposta passa pelo mesmo filtro do editor (`normalizarHtml`): só as tags e cores permitidas entram, então negrito, listas e tabelas se mantêm e nada perigoso passa.
- **Configuração:** `GROQ_API_KEY` nas variáveis de ambiente (Vercel). Sem ela, o botão avisa que a IA de texto não está configurada. No plano gratuito da Groq, os gpt-oss têm 30 pedidos e 8 mil tokens por minuto (cada revisão usa ~1 a 2 mil): o reserva tem limites próprios e ajuda nos picos.
- **Descrição do processo** (05/11/2026, pedido do Rafael): o mesmo botão "Melhorar com IA" fica no título do cartão "Descrição do processo", na página do processo (não aparece com o processo arquivado). O pedido usa `campo: "descricao"`, com o nome do processo, a área e a organização como contexto, e regras próprias: descrever o processo (o que é, onde começa e termina, sistemas e áreas, resultado) em frases completas, sem virar lista de passos e sem resumir. Ao usar a sugestão, a descrição é salva como numa edição normal.
- **Referências na revisão** (vale para passos, objetivo e descrição): as referências a outros documentos (decisão 35) não passam pela IA. Antes do pedido, cada uma vira um marcador `[[REF1]]`, `[[REF2]]`…; na volta, o marcador dá lugar à referência original (tipo, id e relação). Se a IA perder, repetir ou inventar um marcador, a sugestão é descartada e vai para o modelo seguinte; se nenhum acertar, a pessoa vê "A IA mexeu nas referências a outros documentos…" e o texto não muda.

## 31. Modelo da plataforma: duas frentes por processo, arquivar, gravação do POP (03/11/2026)
- **O modelo, nas palavras do Rafael:** o Fluxi documenta e organiza o conhecimento operacional de uma empresa, da estrutura da organização até a instrução detalhada de cada tarefa. A estrutura é hierárquica: organização → áreas (setores) → processos. O **processo é a unidade central**; tudo o que vem abaixo pertence a um processo. Cada processo tem **duas frentes que convivem lado a lado**: os **recursos do processo** (visão macro: o fluxograma, desenhado à mão ou com IA, publicado online para consulta) e a **gestão dos POPs** (visão micro: cada POP ensina a executar uma atividade, com gravações de tela, publicação online, PDF/DOCX e IA de apoio). O fluxograma e os POPs **não se ligam etapa a etapa**: só coexistem no mesmo processo. Cada POP **pertence a uma única área**, pelo processo em que foi criado (responsável por elaborar e manter), mas **pode ser consultado por toda a empresa**.
- **Um fluxograma por processo** (índice único em `fluxogramas.processo_id`). "Gerar de novo com IA" substitui o desenho atual mantendo id e código; não há versões de fluxograma. Sai o "duplicar". O POP não escolhe mais fluxograma: o documento (PDF/DOCX) aponta sozinho para o fluxograma do processo. O editor do POP mostra esse fluxograma só como informação (bloco "Fluxograma do processo": nome, origem, data e onde ele aparece) ou avisa que o processo ainda não tem um. O código do POP e o do fluxograma novos são o código do processo; os que já existiam ficaram como estavam (o código está nos documentos já emitidos).
- **Gravação de tela pertence ao POP** (`gravacoes.pop_id`; o processo vem do POP). É feita só a partir do POP, e um POP pode ter várias. **A gravação não gera mais POP nem fluxograma com IA** (decisão 14 fica superada nessa parte): o POP é escrito à mão, com a correção de texto da decisão 30; as telas marcadas viram prints dos passos ("Levar telas para os passos" ou "Anexar print → Tela da gravação"). A **transcrição é feita sob demanda** (botão na gravação) e serve para gerar o fluxograma do processo com IA. A IA dentro do POP (escrever a partir da gravação, apoio no uso) fica para depois.
- **Arquivar em vez de excluir**, para processo e POP: some das listas com tudo o que tem dentro, sem apagar; dá para restaurar. Só o que está arquivado pode ser **excluído definitivamente**, com confirmação, e aí vai tudo junto (POPs, gravações com vídeo e telas, fluxograma). Nunca sobra item sem processo (a regra "excluir só a pasta" da decisão 15 fica superada).
- **Página do processo em duas frentes** (Recursos do processo; POPs do processo, com "Novo POP" como caminho único). **Menu** sem as listas gerais de gravações e fluxogramas: eles vivem dentro do POP e do processo. Ficam Início, POPs e Organizações.
- **Publicação online (a fazer):** o POP e o fluxograma publicados ganham uma página de consulta com **link público para qualquer pessoa**, com código longo e não adivinhável no endereço. Decisão registrada para quando a plataforma fechar: a mesma página passa a pedir login, com a regra **consultar, toda a organização; editar, só a área dona** (isso muda o modelo de acesso da decisão 16, que previa ver/editar por organização ou área).
- **IA no uso do POP (a fazer, sem data):** apoio a quem consulta o POP (perguntar, resumir, ser guiado passo a passo). Registrada, não implementada.
- **Dados existentes:** POP "Lançamento de Notas Fiscais" foi para um processo novo na área Controladoria Administrativa; a gravação de teste de 29/10 foi excluída; a gravação "Vale transporte" passou a ser a segunda gravação do POP de Cadastro de Vale-Transporte; o fluxograma "Feirão da Casa Própria" vai para um processo próprio (migração `0012_arquivar.sql` e ajustes pela API).

## 32. Publicação online do POP e do fluxograma (03/11/2026)
- **Página pública do POP** em `/p/<link>`: link longo e aleatório (`pops.link_publico`, 32 caracteres), aberto para quem o tiver (decisão 31); quando a plataforma fechar, a mesma página passa a pedir login. Fora do app (sem menu), funciona no celular e não é indexada por buscadores. Mostra a versão publicada: dados do POP, objetivo, envolvidos, procedimentos com os prints (já marcados), histórico de revisões, o **fluxograma do processo** e os botões de PDF e DOCX dessa versão. Só POP publicado e não arquivado; senão, "Este POP não está disponível".
- **Versão publicada** (escolha do Rafael): ao clicar em "Publicar", o Fluxi guarda uma cópia do POP (`pops.publicacao`) e copia os prints para `tenants/<conta>/publicacoes/<pop>/`, então editar, trocar ou marcar um print depois não muda o que está publicado. A página mostra essa cópia até alguém publicar de novo. No editor: "Alterações não publicadas" e "Publicar alterações" quando o conteúdo (inclusive as marcações dos prints) ficou diferente do publicado. ("Tirar do ar", que voltava para rascunho, foi trocado pela chave online/offline da decisão 34.) POP marcado como publicado antes desta decisão ganha a cópia na primeira visita à página pública. O PDF e o DOCX baixados no app continuam saindo do conteúdo atual (o da área); os da página pública saem da versão publicada.
- **"Copiar link público"** no editor do POP e um botão para abrir a página pública (desde a decisão 34, na faixa "Página pública", ao lado da chave online/offline).
- **Fluxograma em SVG:** não há conversor de draw.io para servidor que rode na Vercel (o oficial é o app de computador). O editor embutido (`embed.diagrams.net`) exporta SVG pela ação `export` com `format: 'svg'` e `embedImages: true`: vetor, nítido em qualquer zoom, e **mantém a animação das setas** (Flow Animation), como confirma a documentação do draw.io. O editor gera e salva o SVG (`fluxogramas.svg`) ao abrir e a cada salvamento; "Gerar de novo com IA" apaga o SVG antigo e o editor, que abre em seguida, gera o novo. O fluxograma é do processo e aparece sempre na última versão salva.
- **Página pública só do fluxograma** em `/f/<link>` (`fluxogramas.link_publico`), com "Ajustar à tela", "Tamanho real" e o download do SVG: é para onde o **"Abrir diagrama" do PDF e do DOCX** leva (antes levava ao editor interno). O SVG é servido como imagem (`<img>`) e com política de segurança que só deixa passar estilos: a animação roda e nenhum código embutido no arquivo é executado.


## 33. Fluxograma não vem de gravação de tela (03/11/2026)
- **Regra do Rafael:** "um fluxograma não pode surgir através de gravação de tela". A gravação de tela serve só ao POP: o vídeo com a narração e as telas marcadas, que viram os prints dos passos.
- **Sai a transcrição da gravação** (a parte da decisão 31 que a fazia sob demanda para gerar o fluxograma): a tela da gravação não tem mais "Transcrever a narração" nem o texto transcrito, a página do processo não abre mais o "Gerar com IA" a partir de uma gravação (`?gerar=`) e o diálogo do fluxograma não lista gravações. Saem a rota `POST/GET /api/gravacoes/:id/processar` e `lib/server/processamento.ts`.
- **O "Gerar com IA" do fluxograma continua** com as três fontes que não são gravação de tela: descrição do processo, transcrição de reunião (colada ou em arquivo) e áudio/vídeo de reunião.
- **Banco:** nada foi apagado. As colunas de transcrição (`gravacoes.processamento`, `gravacao_segmentos.transcricao_id`, `transcricao_status`, `falas`) e as transcrições já feitas ficam guardadas, sem uso.


## 34. Excluir gravação e chave online/offline do link público (03/11/2026)
- **Excluir gravação** (pedido do Rafael: excluir de vez, com confirmação, sem arquivar). Botão "Excluir gravação" (vermelho, sem fundo) no topo da tela da gravação: só ali, depois de abrir a gravação (a lista de gravações do editor do POP não tem lixeira, pedido do Rafael). Antes, um pop-up de confirmação diz o nome da gravação, que o vídeo e as telas marcadas são apagados para sempre e quantas telas já estão nos passos do POP.
- **As telas que estão nos passos não se perdem** (138 passos em produção usavam prints de gravações): ao excluir, elas passam a ser do POP (`gravacao_marcacoes.gravacao_id` → `pop_id`), como um print anexado; o arquivo fica onde está, então os passos, a impressão digital da versão publicada e o PDF/DOCX não mudam. Uma tela usada em outro POP do mesmo processo vai para esse POP. O vídeo e as telas que não estão em passo nenhum são apagados. Ao excluir o POP depois, essas telas são apagadas pelo caminho (não só pela pasta do POP). Quando o próprio POP ou o processo é excluído, a gravação vai junto sem preservar nada (`excluir(id, { preservarTelas: false })`).
- **Chave da página pública** (`pops.link_publico_ativo`, migração 0014, já aplicada): faixa "Página pública" logo abaixo do topo do editor do POP, com uma chave ON (verde, "Página pública online") / OFF (vermelha, "Página pública offline"), uma frase que diz o efeito, "Copiar link" e o botão de abrir. ## 35. Referências entre POPs e processos e página pública do processo (04/11/2026)
- **O que é:** dentro do texto de um POP (objetivo e passos) ou da descrição de um processo, a pessoa cita outro POP ou processo com o botão **"Referência"** da barra do texto rico. A referência é um **chip** no texto, com o tipo de relação, e na página pública vira um link para o documento citado. Composição (processo com os POPs dele) continua automática, pela estrutura; não precisa de referência.
- **Tipos de relação** (escolhidos ao inserir; mudam pelo menu do chip), cada um com cor e ícone (Tabler, escolhidos pelo Rafael): **Próxima etapa** (verde, seta tracejada para a direita), **Etapa anterior** (cinza, seta tracejada para a esquerda), **Depende de** (laranja, triângulo de alerta) e **Consulta** (azul, seta curva para cima). No PDF e no DOCX vai só o rótulo, na cor. Em "Referenciado em" aparece o inverso: "Próxima etapa de", "Etapa anterior de", "Pré-requisito de", "Consultado em". As cores e rótulos são os mesmos no editor, nas páginas públicas, no PDF e no DOCX (`lib/referencias.ts`).
- **Formato no texto:** `<a data-ref="pop:<id>" data-rel="proxima">rótulo</a>` dentro do HTML do campo (`lib/pop/texto-rico.ts`). O destino é guardado **por id**; o rótulo guardado é só reserva: o nome, a identificação e a situação são resolvidos ao mostrar, então renomear um POP atualiza as referências a ele. No editor o chip é um nó atômico do TipTap (`components/pop/Referencia.tsx`); clicar abre o menu (tipo, abrir, remover). O seletor (`SeletorReferencia.tsx`) busca por nome, identificação ou código em **todas as áreas e organizações** (todos podem consultar, decisão 31), mostra o tipo, onde fica e se a página pública está no ar (bolinha verde "Online"; vermelha "Não publicado" ou "Offline"), e nunca lista o próprio documento.
- **Índice derivado:** ao salvar, o servidor extrai as referências do texto para a tabela `referencias` (origem, destino, relação, campo). O texto é a fonte; a tabela responde "Referenciado em" (editor e página pública) e o aviso ao arquivar ou excluir ("este POP é referenciado em N documentos"). Excluir de vez tira o documento do índice. Referência a um destino que deixou de existir aparece como "documento excluído", sem link.
- **Página pública:** o chip leva a `/p/<link>` ou `/pr/<link>` com `?de=<p|pr>:<link da origem>`; a página de destino mostra **"← Voltar para …"** (nome atual da origem, só se ela também está no ar). Decisão do Rafael: destino não publicado ou offline **mantém o link**, que abre a página "não disponível" (com o mesmo "Voltar"). Só destino excluído fica sem link.
- **Página pública do processo** (`/pr/<link>`, `processos.link_publico`, migração 0015): nome, código, área, descrição (com as referências), fluxograma (o SVG) e os POPs **publicados e online**, cada um levando à página pública do POP. A publicação de cada POP continua dentro do POP. O processo tem a mesma chave ON/OFF da página pública (`processos.link_publico_ativo`), ligada por padrão. Na página pública do POP, o nome do processo no caminho do topo vira link para ela.
- **Descrição do processo:** o campo `descricao` (existia no banco, sem tela) passa a ser texto rico com o botão de referência, na página do processo, salvo 1 s após a última alteração. Aparece na página pública do processo.
- **PDF e DOCX:** a referência sai como "Relação: POP MKT-002 · Nome" na cor da relação, sublinhada e com link para a página pública do destino quando ela existe (hyperlink no DOCX, anotação de link no PDF). A versão publicada guarda o chip no conteúdo; nome e link são resolvidos na hora de gerar.


## 36. Mover ou copiar POPs e processos (04/11/2026)
- **O que é** (pedido do Rafael): um diálogo **"Mover ou copiar"** (`components/MoverCopiar.tsx`) com duas abas. **POP:** para outro processo, de qualquer área ou organização. **Processo:** para outra área. Fica no editor do POP, na lista de POPs e na página do processo (o seletor de área da página do processo continua fazendo o "mover" rápido). O diálogo mostra onde o item está, lista os destinos agrupados (processos por "Organização › Área"; áreas por organização), marca o destino atual como "(atual)" e resume o que vai acontecer antes de confirmar.
- **Mover o POP** (`POST /api/pops/:id/mover`, agora com `processo_id`): o POP sai do processo atual e entra no escolhido, com as gravações de tela dele (`gravacoes.processo_id`). O código do processo no documento e o campo "Área" (se ainda estava com a área antiga, regra da decisão 25) acompanham; link público, status, versão, histórico e prints não mudam. - **Copiar o POP** (`POST /api/pops/:id/copiar`): cria um POP novo no processo escolhido (pode ser o mesmo; aí o nome ganha "(cópia)"), como **rascunho**, versão 1.0, histórico recomeçando na Rev. 01, com os textos, os envolvidos, as referências (que entram no índice) e os **prints**: cada print usado nos passos é copiado para a pasta do POP novo como tela dele (`gravacao_marcacoes.pop_id`), com a marcação desenhada; o mesmo print usado em dois passos é copiado uma vez. A identificação vem igual (a pessoa ajusta se a área usa outra numeração). Gravações de tela e a publicação não vão: a cópia tem link público próprio e começa fora do ar até ser publicada. Se um arquivo não puder ser copiado, o passo fica apontando para o print original (aviso no log) e a cópia é criada mesmo assim.
- **Mover o processo:** é o `PATCH /api/processos/:id` com `area_id` que já existia (o campo "Área" dos POPs acompanha, decisão 25); o diálogo só mostra antes o que vai junto (POPs, gravações, fluxograma) e que os links públicos continuam.
- **Copiar o processo** (`POST /api/processos/:id/copiar`, `lib/server/copia.ts`): processo novo na área escolhida (mesma área: "(cópia)"), com código e link público próprios, a descrição (referências indexadas), o fluxograma (desenho, esquema, miniatura e SVG publicado, com o código do processo novo) e cópias dos **POPs ativos** (arquivados não vão), pela mesma regra da cópia de POP. Gravações de tela não vão.
- **Nome da cópia:** o diálogo sugere o nome atual (ou "Nome (cópia)" no mesmo destino) e a pessoa pode mudar antes de confirmar. Ao terminar, mover recarrega a tela; copiar abre a cópia.

## 39. Entrevista por voz com a IA (06/11/2026) — protótipo
- **Ideia do Rafael:** a IA entrevista, por voz e ao vivo, quem executa o processo, como um consultor faria: pergunta, aprofunda, identifica etapas, responsáveis, ferramentas, entradas, saídas, regras, exceções e dificuldades. Nada precisa aparecer na tela durante a conversa; o resultado é processado quando a chamada termina. Primeiro dentro do INCFlow; Google Meet e Teams ficam para depois (serviço Recall.ai, ≈ US$ 0,60/h a mais).
- **Pesquisa (06/11):** a AssemblyAI cobre a escuta ao vivo (Universal-3.6 Pro Realtime, com português) e, desde 27/10/2026, a voz (AssemblyAI-TTS-1, português); o produto "tudo em um" deles (Voice Agent API) está sendo aposentado, então a montagem é em peças: ouvir → pensar (Claude) → falar. A integração nativa com o Meet (só recebe áudio, em teste fechado) e com o Teams (C#/Windows Server, não recomendada pela Microsoft para agentes de IA) foi descartada.
- **Como funciona:** no processo, "Entrevista com IA" → página `/app/entrevistas/<id>` com três telas: a abertura (o que vai acontecer, ciência de que a conversa é gravada e processada por IA, microfone), a conversa (só o estado: a IA fala, ouve ou pensa, o número de perguntas, o tempo e os tópicos cobertos; nenhum texto) e o resultado.
  - O **navegador liga direto na escuta** da AssemblyAI (WebSocket) com um token temporário que o servidor pede (vale 60 s para abrir; a sessão dura no máximo 2 h). O microfone vira PCM 16 kHz num AudioWorklet (`public/entrevista/captura.js`). A Vercel só responde chamadas curtas (turno: até 60 s; encerrar: até 300 s): não há servidor extra.
  - Quando a escuta avisa que a pessoa terminou (`end_of_turn`), a página espera 0,9 s (ela pode continuar a frase) e manda o texto ao servidor; o Claude (Haiku 5.5, sem raciocínio estendido, para responder rápido) recebe a conversa inteira, a lista de tópicos cobertos e as anotações, e devolve a próxima fala, os tópicos cobertos e uma anotação; a fala vira WAV pela voz da AssemblyAI (`aai-benicio`) e toca. Sem voz do servidor, usa a voz do navegador; sem nenhuma, a pergunta aparece na tela.
  - Enquanto a IA fala ou pensa, o microfone manda **silêncio** (a escuta não ouve a própria IA). Nesta versão a pessoa não interrompe a IA. A escuta espera mais antes de encerrar uma fala (`min_turn_silence` 400 ms, `max_turn_silence` 1600 ms), recebe os nomes do processo, da área, da organização e dos POPs (`keyterms_prompt`) e a pergunta que acabou de ser feita (`agent_context`). Se ninguém fala por 30 s, a IA repete a pergunta uma vez.
  - A conversa (os dois lados) é gravada no navegador e vai para `tenants/<tenant>/entrevistas/<id>/conversa.webm` ao encerrar, para ouvir depois (e, no futuro, transcrever de novo com o modelo em lote).
  - **Ao encerrar** (a IA se despede, ou a pessoa clica em Encerrar): o Claude Sonnet 5.5 lê a conversa inteira e devolve a descrição do processo (HTML limpo: só `p`, `ul`, `ol`, `li`, `strong`, `em`), a ficha (objetivo, início, resultado, etapas com responsável, ferramentas, entradas, saídas, regras e exceções, dificuldades) e as pendências (perguntas para uma próxima conversa). Na tela: "Usar como descrição do processo" (confirma se já existe uma), "Gerar fluxograma" pela transcrição (a geração que já existia), a conversa transcrita e o áudio. Se o processamento falhar ou for interrompido, dá para gerar de novo; a conversa fica guardada.
- **Custo estimado por hora de entrevista:** escuta US$ 0,45 (`INCFLOW_MODELO_ESCUTA=universal-streaming-multilingual` baixa para US$ 0,15), voz ≈ US$ 0,25 (US$ 15 por milhão de caracteres), conversa e análise ≈ US$ 0,20 a 1,50 conforme o uso: cerca de **US$ 1 a 2 por hora**. A escuta é cobrada pelo tempo de conexão aberta, por isso a página encerra a sessão (`Terminate`) ao sair.
- **Configuração:** `ASSEMBLYAI_API_KEY` e `ANTHROPIC_API_KEY` (já existem). Opcionais: `INCFLOW_MODELO_ENTREVISTA`, `INCFLOW_MODELO_ANALISE`, `INCFLOW_MODELO_ESCUTA`, `INCFLOW_VOZ_ENTREVISTA`. Dados: tabela `entrevistas` (migração 0016). LGPD: consentimento na abertura; na conta da AssemblyAI, conferir se o uso dos dados para treino está desligado (planos pagos) e pedir retenção zero no streaming.
- **O que o piloto precisa validar (próximos passos):** precisão da escuta em português com o vocabulário da INC; sotaque da voz (se soar lusitana, trocar só a voz); a demora percebida entre a resposta e a próxima pergunta (hoje ≈ 3 a 5 s); permitir interromper a IA; transcrever a gravação com o modelo em lote e separação de falantes; entrevistas pelo Meet e Teams (Recall.ai); cobrança por créditos.

## 40. Entrevista: microfone sempre aberto, interrupção e o caminho para o full duplex (07/11/2026)
- **Especificação do Rafael (pesquisa com outra IA):** a conversa deve ser *full duplex*: a IA continua ouvindo e entendendo enquanto fala, a pessoa pode falar por cima, e o que ela diz entra no contexto sem depender de cancelar a fala da IA. Três níveis: A) áudio nos dois sentidos; B) interrupção (detecta a fala, corta a IA, responde); C) compreensão simultânea. O requisito central é o C; a cadeia STT → LLM → TTS pode existir por dentro, mas não como base da experiência.
- **O que a versão 39 fazia:** nem o B: o microfone mandava silêncio enquanto a IA falava.
- **O que muda agora (B, com o conteúdo aproveitado):** o microfone fica aberto o tempo todo; o cancelamento de eco do navegador (`echoCancellation`) tira a voz da IA da escuta, e um filtro descarta o que sobrar de eco (trecho cujas palavras estão quase todas na fala da IA). Fala de verdade por cima da IA (duas palavras ou mais) **pausa a voz na hora**, marca o turno com `interrompeu` e a fração da fala que chegou a tocar (`ouviu`), e a IA responde ao que a pessoa disse sem repetir o que foi cortado (regra no prompt; a transcrição mostra "interrompeu o entrevistador, que tinha falado cerca de 40% da fala anterior"). O que a pessoa fala enquanto a IA pensa fica na fila e é respondido em seguida. Interromper a despedida cancela o encerramento. A tela mostra o tempo de resposta (do fim da fala da pessoa ao início da voz da IA) e o número de interrupções, as métricas da especificação.
- **Pesquisa dos motores (07/11, documentação oficial):** OpenAI Realtime API, Gemini Live API e ElevenLabs Agents são **interrupção** (cancelam a resposta e respondem depois); o ElevenLabs é uma cascata com modelo de turnos. A AssemblyAI é cascata (não tem modelo fala-para-fala; é "aposta para 2027"). O **GPT-Live** (OpenAI, `gpt-live-1`) é o único de fornecedor grande documentado como full duplex: "ouve e fala ao mesmo tempo", trata interrupções e *backchannels* por prompt, e tem modo de **delegação pelo cliente**, em que a "cabeça" da entrevista (nosso prompt, tópicos, anotações) continua no nosso servidor, recebendo as transcrições e devolvendo o que falar; vozes em português do Brasil (Bossa e Tempo); WebRTC no navegador; US$ 0,05 por minuto de sessão (cobrado por segundo) mais o modelo de apoio. Pontos a confirmar: a documentação não diz explicitamente que a fala sobreposta entra no contexto sem cancelar nada (é o que o teste de aceitação vai medir), nem a lista de idiomas de entrada. O Moshi (Kyutai, código aberto) é full duplex de verdade, mas é pesquisa (GPU de 24 GB, sem português documentado).
- **Plano:** (1) esta versão, com a cascata da AssemblyAI, já permite rodar o teste de aceitação da especificação (a pessoa fala por cima; a informação é aproveitada) e medir latência e interrupções. (2) Um segundo motor, GPT-Live com delegação pelo cliente, atrás da mesma "cabeça" da entrevista e do mesmo processamento final, para comparar lado a lado no mesmo roteiro; precisa de `OPENAI_API_KEY`. (3) Só depois: criar processo e POP a partir do resultado.

## 41. Entrevista só com o GPT-Live (OpenAI), fora do processo (07/11/2026)
- **Pedido do Rafael:** "tira da Assembly e deixa somente da OpenAI", e testar fora da criação de processo, para não aumentar o custo. Primeiro a implementação, os testes e a informação gerada; criar processo e POP fica para depois.
- **Motor de voz:** só o **GPT-Live** (`gpt-live-1`), o modelo full duplex da OpenAI (decisão 40). A AssemblyAI saiu da entrevista (escuta, voz, token e a conversa turno a turno com o Claude Haiku); ela continua só na transcrição das gravações de tela (decisão 4).
- **Como funciona:** o navegador fala direto com o GPT-Live por **WebRTC**: o áudio vai e volta ao mesmo tempo, e quem decide parar, encaixar uma correção ou seguir falando é o próprio modelo. O servidor só abre a sessão (`POST /api/entrevistas/:id/sessao`: recebe a oferta WebRTC do navegador, chama `POST https://api.openai.com/v1/live/sessions` com a chave, que não vai para o navegador, e devolve a resposta). A condução da entrevista está nas **instruções da sessão** (papel, tema, contexto, tópicos, regras de conversa ao vivo: ouvir enquanto fala, incorporar correções, não tratar "aham" como interrupção; a despedida termina com a frase "Entrevista concluída."). Sem trabalho de apoio (`delegation: client`, sem consultas); se o modelo pedir uma, o app responde que não há o que consultar. `store: false`: a OpenAI não guarda a sessão. O canal de dados do navegador só pode encerrar a sessão e pedir uma fala (se a IA não abrir a conversa em 3 s, o app pede a abertura). Voz `bossa` (português do Brasil; `tempo` é a outra).
- **O que volta:** pelo canal de dados chegam os pedaços de transcrição dos dois lados com o tempo de cada um (`session.input_transcript.delta`, `session.output_transcript.delta`); o navegador junta os pedaços em falas (`lib/entrevista/conversa.ts`), marca as falas da pessoa feitas **enquanto a IA falava** (`sobreposta`) e calcula as métricas da especificação: reação da IA (do fim da fala da pessoa ao início da fala da IA), falas sobrepostas, duração (pelo uso que a OpenAI informa) e custo da voz. A conversa e as métricas são guardadas a cada 15 s e no fim (nada se perde se a página fechar). A gravação (os dois lados) vai para o Storage, um arquivo por sessão. Eventos que o app não conhece e erros da sessão ficam num "diagnóstico" no resultado, para ajustar depois.
- **Fim:** quando a IA diz a frase final e os dois ficam 2,5 s em silêncio, a entrevista encerra sozinha; também há o botão "Encerrar entrevista" e um teto de 45 minutos (custo). Ao encerrar, o Claude Sonnet 5.5 lê a conversa (as falas sobrepostas valem como correção) e gera a descrição, a ficha e as pendências, como antes.
- **Fora do processo:** a entrevista não pede processo (migração 0017: `processo_id` opcional, `tema`, `contexto`, `sessoes`, `metricas`, `motor`). Entrada pelo menu, em "Laboratório" → "Entrevista com IA" (`/app/entrevistas`): tema e contexto, e a lista das entrevistas. O resultado mostra só a informação gerada; os botões de usar a descrição no processo e de gerar o fluxograma saíram, e a entrevista saiu da página do processo.
- **Custo:** voz US$ 0,05 por minuto de sessão, cobrado por segundo (≈ US$ 1,50 numa entrevista de 30 min; a abertura cobra 15 s), mais a análise no fim (centavos). Continuar uma entrevista abre outra sessão, com o histórico da conversa.
- **Configuração:** `OPENAI_API_KEY` (Vercel). Opcionais: `INCFLOW_VOZ_ENTREVISTA` (`bossa` ou `tempo`), `INCFLOW_MODELO_VOZ`, `INCFLOW_MODELO_ANALISE`.
- **Validado contra a API real (07/11):** abertura de sessão por WebRTC com o corpo exato do servidor (primeira vez e continuação com histórico), vozes `bossa` e `tempo`, canal de dados restrito. O áudio em si só dá para testar no navegador de verdade (o ambiente de desenvolvimento não deixa a conexão de mídia passar).

Reage às duas vozes: a malha ondula com a voz da IA e as partículas se aproximam e brilham com a voz da pessoa (o motor manda o volume dos dois lados 20 vezes por segundo). Em "processando", pulsa sozinha; com `prefers-reduced-motion`, movimento reduzido.
- **IA menos passiva:** no teste, uma vez ela ficou só no "aham" esperando. Instrução nova: quando a pessoa termina (pausa de uns dois segundos), a vez é da IA, que reage em poucas palavras e faz a próxima pergunta; se a pessoa perguntar o que ela quer saber, responde com uma pergunta concreta.
- **Transcrição:** os "aham" da IA não cortam mais a fala da pessoa em pedaços (uma fala curta do outro lado não muda a vez) e ficam marcados como `apoio`: aparecem discretos na conversa transcrita, não vão para a análise e são contados à parte ("sinais de escuta").
- **Métricas:** a reação da IA passa a ser medida só nas respostas de verdade (sem os apoios); as "falas por cima da IA" contam também quando a pessoa entra numa pausa curta (até 1,5 s) de uma fala da IA que não tinha terminado em pergunta, que é como uma interrupção aparece quando a IA para para ouvir.

## 43. Entrevista: segundo teste real, interrupção, ritmo e indicadores de custo (07/11/2026)

Interruption policy: parar imediatamente, mesmo no meio da frase, quando a pessoa falar por cima (correção, dúvida, pedido ou "espera"); só "aham"/"uhum"/"sei"/"tá" breves não interrompem. Jeito de falar: frases completas e fluidas, pausas só entre frases, sem muletas; responder assim que a pessoa terminar, sem esperar (saiu a regra dos "dois segundos"). Delegation policy: nunca gerar `<|SpawnThinking|>` (não há trabalho de apoio; evita demora).

- **Indicadores e custos (pedido do Rafael: acompanhar todos):** reação da IA (mediana e máxima), falas por cima da IA, tempo de fala de cada lado (e a parte da pessoa), sinais de escuta e maior silêncio, duração e sessões, custo da voz (US$ 0,05/min), custo da análise (tokens de entrada e saída do Claude, pela tabela da Anthropic de 06/10/2026: Sonnet 5.5 US$ 2/10 por milhão, cache US$ 0,20) e custo total. A lista de entrevistas mostra o acumulado (entrevistas, tempo de voz, custo da voz e total). Erros do navegador ao começar (microfone, conexão) entram no diagnóstico.

## 46. Entrevista: pausar e continuar depois, sem custo parado, e sinais de escuta variados (07/11/2026)
- **Quinto teste ("compra de terrenos", 5 min, US$ 0,27):** a abertura caiu de 3,4 s para 0,6 s e a JOI se apresentou como pedido; quando a pessoa foi chamar o Ronaldo, ela esperou em silêncio, cumprimentou o Ronaldo pelo nome e retomou a pergunta; a consulta do Zenkit saiu sem pausa. - **Pausar e continuar depois** (pedido do Rafael, com a condição de não deixar custo correndo): quando a pessoa precisa sair antes de cobrir os tópicos, a JOI diz o que ficou faltando e se despede com "a gente continua depois" (se a pessoa perguntar se ficou dúvida, ela pergunta na hora). Ao continuar, a sessão nova recebe o histórico (sem os "aham") e a instrução de mostrar que lembra ("que bom que você voltou", onde pararam, o que faltava), sem repetir a apresentação; se for outra pessoa, ela se apresenta e pergunta o nome. O resultado mostra quantas sessões foram desligadas com confirmação da OpenAI (os eventos agora somam todas as sessões). A OpenAI não tem como consultar ou fechar uma sessão pelo servidor (testado: o endereço de sessões só aceita WebSocket), então o controle fica no navegador.
- **Sinais de escuta:** a Backchannel policy pede sinais variados e poucos (alternar "aham", "uhum", "sei", "certo", "entendi", "faz sentido", "ah, legal" e silêncio; nunca o mesmo duas vezes seguidas) e começos de resposta variados. - **Conexão (a monitorar):** a Vercel não fica no meio da conversa: o áudio vai direto do navegador para a OpenAI; a Vercel só abre a sessão e guarda a conversa. Para achar os 7,5 s, cada etapa passa a ser medida: microfone, conexão WebRTC, ida ao servidor (e, dentro dela, quanto foi a OpenAI) e início da sessão.

## 53. Entrevistas da Maia dentro do processo, por convite (09/11/2026)

- **Decisão do Rafael:** a entrevista existe para compreender e analisar um **processo** (não um POP), então cada entrevista pertence a um processo e nasce dentro dele, por convite. O administrador ou gestor abre o processo, escolhe **até três pessoas** cadastradas (uma entrevista por pessoa; conversa em grupo, não) e envia o convite; a pessoa recebe um e-mail, entra com o login e liga para a Maia. Um processo pode ter várias entrevistas, com pessoas diferentes, e tudo o que sai delas fica acessível no processo. Níveis de acesso ficam como estão por enquanto (todo logado vê processos e resultados; a diferença é quem convida e quem conversa).
- **Relacionamentos:** processo 1 → N entrevistas; entrevista 1 → 1 entrevistado (`entrevistado_id`); a entrevista guarda quem convidou, quando, a nota do convite e quando o e-mail saiu. Status novo **`convidada`** antes de `em_andamento` (migração 0019). Quem já tem entrevista aberta no processo não recebe outra.
- **O que a Maia recebe:** o tema é o nome do processo; o contexto é montado na hora do convite com organização e área, a descrição do processo (texto puro, até 1.500 caracteres) e o pedido de quem convidou ("foque nas aprovações"). Ela chama a pessoa pelo nome (vem do convite).
- **Acesso (decisão 49 em prática):** só a pessoa convidada abre a sessão de voz, salva a conversa, consulta e grava áudio (o servidor confere a pessoa logada; 403 "outra pessoa"); gestores e administradores convidam, reenviam e cancelam convites, excluem entrevistas e podem gerar o resultado de novo. Quem abre a entrevista de outra pessoa vê de quem é e volta ao processo.
- **Telas:** seção **Entrevistas com a Maia** na página do processo (pessoa, situação, convite, falas, duração, pendências; "Ligar para a Maia" para a própria pessoa; reenviar e cancelar para gestores) com o diálogo de convite (busca, até três marcadas, nota); a tela "Entrevista com IA" perdeu o formulário solto e mostra "Suas entrevistas" e as demais, com o processo; o Início avisa "A Maia está esperando você…"; a página da entrevista mostra o processo no caminho e o pedido de quem convidou. O Painel da Maia ganhou o processo.
- **E-mail:** o convite sai por um **workflow próprio** do Pipedream, separado do de login, com URL e segredo próprios (`CONVITE_MAILER_URL`, `CONVITE_MAILER_SECRET`; decisão do Rafael, para um não mexer no outro). `lib/server/carteiro.ts` escolhe o carteiro pelo tipo da mensagem. O convite leva um botão para `/app/entrevistas/<id>` (o `validar_convite` só aceita links https para o host do app). Se o e-mail falhar, ou se o carteiro ainda não estiver configurado em produção, o convite fica criado "sem e-mail", a tela avisa e dá para reenviar. O endereço do app nos links vem de `INC_APP_URL` ou da origem do pedido. Guia: `docs/convites.md`.

## 54. Quem controla as entrevistas: o administrador gere, ninguém edita a conversa (09/11/2026)

- **Decisão do Rafael:** os administradores têm controle total das entrevistas, até excluir, mas não sobre o conteúdo gerado da conversa.
- **Administrador:** convida, reenvia, cancela convites e **exclui qualquer entrevista**, em qualquer situação (convidada, pausada, concluída, com erro), no processo, na tela de entrevistas e no Painel da Maia. Excluir apaga tudo (conversa, áudio e resultado) e pede confirmação. Não exclui enquanto a pessoa está na ligação (a conversa foi salva há menos de um minuto) nem enquanto o resultado está sendo gerado (409, "tente de novo em alguns minutos").
- **Gestor:** convida, reenvia e cancela convites pendentes; não exclui entrevista que já começou (403).
- **Ninguém edita o conteúdo:** a conversa (falas, áudio) só é gravada pela própria pessoa entrevistada, durante a ligação; o resultado é da Maia e, concluída a entrevista, não muda. Não há tela nem rota para editar transcrição ou resultado. Administradores e gestores só **geram de novo um resultado que falhou** (erro ou processamento parado); não encerram a conversa de outra pessoa nem refazem um resultado pronto.

## 66. Os pontos em aberto param de se multiplicar (10/11/2026)
- **O que o Rafael viu (testes com o Rodrigo Agreli):** a conversa entrava num ciclo: voltava à ligação para responder os pontos em aberto e, no fim, apareciam pontos novos. A entrevista de Férias passou por sete análises e terminou com seis pendências; a do eSocial, por quatro.
- **A causa, lendo as conversas:** a cada volta a análise relia a conversa inteira e escrevia a lista de pendências do zero. Com isso: (1) reabria o que já tinha sido respondido, tratando a resposta nova como "contradição" com o que foi dito antes (o prazo de trinta dias, respondido três vezes); (2) não aceitava resposta curta ou negativa ("não costuma dar problema" voltava como pergunta); (3) transformava em dúvida falas de fundo que o microfone captou, sem ligação com a pergunta ("as vagas", "tinha que ser semanal"); (4) acrescentava curiosidades novas a cada rodada.
- **Depois de uma volta, a lista só diminui.** A análise recebe as pendências anteriores numeradas (com as que a pessoa escolheu responder marcadas) e devolve a situação de cada uma: respondida, em aberto ou "ela não sabe, é com outra pessoa". A lista nova é montada pelo código a partir daí (`pendenciasDepoisDoComplemento`): respondida sai; o que ela não sabe vai para "Para outra pessoa responder"; o resto fica. Pendência nova não entra, nem que a IA escreva uma. A descrição e a ficha continuam sendo refeitas com a conversa inteira.
- **Na primeira análise, menos pendências e melhores:** só o que faz falta para descrever o processo (etapa sem responsável, caminho de decisão sem explicação, prazo ou regra citada sem dizer qual), no máximo cinco. Pergunta respondida está fechada, mesmo com resposta curta ou negativa; o que foi dito depois vale sobre o que foi dito antes; curiosidade não é pendência; falas soltas, sem ligação com a pergunta, são ruído e são ignoradas.

## 67. A Maia pergunta quem é a pessoa: área e o que faz (10/11/2026)
- **Pedido:** a Maia pegar a informação da pessoa que ela entrevista: a área ou o setor e um pouco do que ela faz.
- **Na conversa:** na abertura da primeira ligação, depois de se apresentar e avisar da gravação, a Maia pergunta de qual área a pessoa é e o que ela faz no dia a dia, e só então entra no processo. É uma pergunta só; ela não insiste nem aprofunda.
- **No resultado:** a análise guarda `entrevistado` (área e o que faz), só com o que a pessoa contou. O resultado mostra o cartão "Quem foi entrevistado" ("Sobre você", para a própria pessoa); na página do processo, a área aparece ao lado do nome; e o material do fluxograma gerado das conversas (decisão 63) leva essa informação, que ajuda a IA a escolher as raias.
- **Nas próximas entrevistas da mesma pessoa:** a Maia já sabe (lê da conversa concluída mais recente) e não pergunta de novo; a análise recebe o que ela já contou. Não há campo novo no cadastro de pessoas nem migração: fica no resultado da entrevista.

## 68. O fluxograma das conversas usa tudo o que a Maia gerou (10/11/2026)
- **Pergunta do Rafael:** o fluxograma gerado das conversas considera as pendências? Tem que considerar todo o conteúdo gerado.
- **Como estava (decisão 63):** iam a transcrição e parte do resumo: objetivo, início, resultado, etapas (com quem faz, ferramentas, regras e exceções), dificuldades, o que ficou em aberto e as perguntas para outra pessoa. Ficavam de fora a **descrição do processo** que a Maia escreveu, as **entradas e saídas** de cada etapa e a marca de onde a pessoa **voltou à ligação** para completar.
- **Como ficou:** de cada conversa vão quem é a pessoa (área e o que faz), a descrição do processo, a ficha inteira (etapas com quem faz, ferramentas, entradas, saídas, regras e exceções), as dificuldades relatadas, o que ficou em aberto, as perguntas para outra pessoa e a transcrição inteira, com a marca da volta ("o que ela disse daqui em diante vale sobre o que disse antes").
- **Como a IA usa cada parte:** a transcrição é a fonte e o resumo organiza; o que foi dito depois vale sobre o que foi dito antes. Pontos em aberto e perguntas para outra pessoa nunca viram resposta inventada: quando tocam uma etapa ou decisão, viram **alerta** no nó, com a pergunta; se uma decisão tem um caminho que ninguém explicou, ela é desenhada com o caminho conhecido e o alerta nela; ponto que não muda o desenho não vira anotação. Dificuldades relatadas viram **nota** curta no nó em que acontecem. A área da pessoa ajuda a saber de quem é a raia quando ela diz "a gente".

## 69. "Em andamento" é só com a pessoa na ligação, e aí ninguém mais entra (11/11/2026)
- **Pedido do Rafael:** uma entrevista que estava acontecendo aparecia como "Pausada". Tem que aparecer como em andamento, com um ícone; e, nesse caso, nem o administrador acessa a conversa até a entrevista terminar.
- **Por que aparecia "Pausada":** o sistema não sabia se a pessoa estava na ligação. Toda entrevista aberta com falas era chamada de pausada; para barrar a exclusão e o encerramento pelo administrador (decisões 54 e 65), o servidor adivinhava pela hora da última gravação (menos de um minuto), o que falhava nos dois sentidos: a conversa só é gravada quando há fala nova, então um silêncio longo parecia pausa, e qualquer gravação recente parecia ligação.
- **O sinal da ligação:** a entrevista ganhou um prazo, `em_ligacao_ate` (migração 0021). Ele nasce quando a sessão de voz abre, é renovado a cada 15 s pelo navegador de quem está falando (junto com a conversa, quando há fala nova, ou por um pulso leve, `POST /api/entrevistas/:id/pulso`, quando não há) e é apagado na pausa, no fim e quando a página fecha (`DELETE …/pulso`). Se o navegador cair sem avisar, o prazo vence sozinho em 45 s e a entrevista volta a "Pausada". Só a própria pessoa acende o sinal.
- **Nas telas:** enquanto o sinal vale, a entrevista aparece como **Em andamento**, num selo verde com o microfone e um ponto que pulsa, na página do processo, em "Conversas com a Maia", na página da conversa e no Painel da Maia. Fora da ligação, a entrevista aberta é "Pausada" (ou "Completar: N pontos"). As listas se atualizam sozinhas (de 10 em 10 s com alguém na ligação, de 30 em 30 s com entrevista aberta), então o selo aparece e some sem recarregar.
- **Ninguém entra durante a ligação:** para quem não é a pessoa entrevistada, inclusive o administrador, a linha da lista fica sem "Abrir" e sem "Excluir" ("Abre quando a ligação terminar") e a página da conversa mostra só o aviso "Fulano está conversando com a Maia agora". O bloqueio é do servidor, não só da tela: a entrevista vem sem as falas, as gravações e o resultado; excluir, encerrar, desfazer o complemento e usar a conversa num fluxograma respondem 409 (`em_ligacao`). Quando a ligação é pausada ou encerrada, a página abre sozinha e o administrador volta a ter o acesso da decisão 65.
- **A própria pessoa nunca fica trancada:** o sinal não bloqueia quem é a pessoa entrevistada (se a aba caiu e o prazo ainda não venceu, ela entra e continua normalmente).
- **Junto:** o administrador não precisa mais esperar um minuto depois da pausa para encerrar ou excluir; e o diálogo "Conversa com a Maia" do fluxograma não lista a conversa que está em ligação.
- **Sem recarregar (pedido do Rafael, no mesmo dia):** o Painel da Maia também se atualiza sozinho, com o mesmo selo. Quem está com a entrevista de outra pessoa aberta (a conversa pausada, o convite pendente ou a página da entrevista no Painel da Maia) percebe sozinho quando a ligação começa: a tela consulta só a situação, de 15 em 15 s (`GET /api/entrevistas/:id/situacao`, leve, sem a conversa), passa para o aviso de bloqueio e volta quando a ligação termina. Durante a ligação, a página da entrevista no Painel da Maia também fica fechada, porque as consultas e os erros guardados nas métricas trazem trechos da conversa.

## 70. O menu lateral é fixo na tela (11/11/2026)
- **Pedido do Rafael:** a sidebar tem que ser fixa. Em "Pessoas e acessos", ao rolar a página, o menu subia e ficava um vão vazio embaixo dele e embaixo do conteúdo. Não pode acontecer em nenhum menu, nem nos próximos.
- **Por que acontecia:** o menu era "grudento" (`position: sticky`), e um elemento grudento só acompanha a rolagem até o fim do bloco que o contém (o layout do app, da altura da janela). A lista de pessoas tem rolagem própria, e o texto invisível que os leitores de tela usam em cada linha ("Acesso de Fulano") ficava posicionado em relação à página inteira: os das linhas escondidas na rolagem da lista esticavam a página para baixo. A página ficava mais alta que o layout; ao rolar além dele, o menu ia junto e sobrava o vão.
- **Como ficou:** no computador, o menu é **fixo na tela** (`position: fixed`), do topo ao rodapé da janela, e o conteúdo começa depois dele (a margem acompanha o menu recolhido). Ele não depende mais da altura de página nenhuma, então nenhuma tela de hoje ou futura o tira de vista. O editor de tela cheia e os diálogos continuam por cima dele. No celular, nada muda: o menu segue sendo a barra do topo.
- **Junto:** o texto para leitores de tela (`.sr-only`) ficou preso no canto, então não estica mais a página nem deixa vão embaixo do conteúdo.
- **Teste:** passa por todas as telas do app (início, áreas, processos, POPs, organizações, conversas com a Maia, pessoas, Painel da Maia, gravação), em duas larguras de computador e no celular: rola até o fim e confere que o menu continua inteiro na tela, que o conteúdo começa depois dele e que não sobra vão embaixo.

## 72. Entrevistas: ativa, arquivada, excluída (11/11/2026)
- **Pedido do Rafael:** organizar o arquivamento e a exclusão das entrevistas. Excluir só de dentro da entrevista e só depois de arquivar; a arquivada sai do processo e vai para uma área própria, com os dados preservados; dá para restaurar. A navegação foi proposta num protótipo clicável (telas reais do app) e aprovada como estava.
- **Os três estados:** *ativa* (no processo), *arquivada* (fora do fluxo, guardada inteira) e *excluída* (apagada de vez). O caminho é sempre ativa → arquivada → excluída; arquivada → ativa é "Restaurar". É o mesmo padrão dos processos e POPs (decisão 31).
- **No processo:** a seção "Entrevistas com a Maia" mostra só as ativas, sem "Excluir" nas linhas. Quando existe alguma arquivada, aparecem as abas **Ativas | Arquivadas**, com a contagem; a aba Arquivadas lista quando e por quem cada uma foi arquivada, com "Restaurar" e "Abrir".
- **Dentro da entrevista:** o botão **Arquivar** fica no alto, à direita, com confirmação (explica que nada é apagado). Arquivada, a página ganha uma faixa com quando e por quem, **Restaurar** e **Excluir definitivamente** (vermelho, com confirmação): a exclusão só existe ali. O resultado e a conversa continuam para consulta; não dá para continuar a ligação, pedir complemento, encerrar nem gerar o resultado de novo.
- **Em "Conversas com a Maia":** as mesmas abas, reunindo as arquivadas de todos os processos.
- **O que a arquivada deixa de fazer no processo:** sai da lista, do fluxograma gerado das conversas e das "Perguntas para outras pessoas"; não impede convidar a mesma pessoa de novo; e a área e a função da pessoa deixam de vir dela.
- **Quem faz o quê:** gestores e administradores arquivam e restauram; só administradores excluem definitivamente. Quem é comum não vê arquivadas: a conversa arquivada some da lista da própria pessoa entrevistada, e pelo endereço direto ela vê só o aviso "Esta conversa foi arquivada". O bloqueio é do servidor, não só da tela.
- **Casos de borda:** a entrevista pausada pode ser arquivada (a pessoa só continua depois de restaurada; se nesse meio-tempo ela foi convidada de novo no mesmo processo, a pausada não volta enquanto a outra estiver aberta). Não se arquiva durante a ligação nem com o resultado sendo gerado. Convite que ainda não começou não tem o que arquivar: continua com "Cancelar" na linha.
- **Painel da Maia:** a arquivada continua na conta dos custos, marcada "arquivada"; o botão de excluir que havia na página da entrevista no painel saiu.
- **Banco:** `arquivado_em` e `arquivado_por` em `entrevistas` (migração 0022).

## 74. Entrevista imediata: o administrador abre a sua na hora, sem convite (12/11/2026)
- **Pedido do Rafael:** quem já conhece o processo e quer ser entrevistado pela Maia precisava se convidar, abrir o e-mail do convite e só então entrar. O fluxo tem que ser instantâneo, sem o autoconvite. Por enquanto, só para administradores.
- **Como ficou:** na página do processo, a seção "Entrevistas com a Maia" ganhou o botão **Iniciar entrevista agora**, ao lado de "Convidar para entrevista". - **Uma aberta por pessoa em cada processo:** se a pessoa já tem uma entrevista aberta no processo (convite pendente ou conversa pausada), o botão leva para ela em vez de criar outra. Com a anterior concluída ou arquivada, abre uma nova.
